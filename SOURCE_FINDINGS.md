# Source-informed save generation findings

Reviewed the local Stardew source at `/home/john/projects/stardew-decomp-clean` without copying game source or assets into this project.

## Canonical new-game path

`Game1.loadForNewGame` constructs the selected farm from its map, adds all locations, calls `AddDefaultBuildings` for every location, then calls `Farm.onNewGame`. It also generates bundles, NPCs, quests, weather/state, and other records. A save template is therefore more than a farm XML fragment.

Relevant source:

- `StardewValley/Game1.cs` — `loadForNewGame`
- `StardewValley/Farm.cs` — `getMapNameFromTypeInt`, `AddDefaultBuildings`, `onNewGame`
- `StardewValley/SaveGame.cs` — save DTO construction and serialization

## Layout IDs and maps

| Save ID | Layout | Map |
|---|---|---|
| `0` | Standard | `Farm` |
| `1` | Riverland | `Farm_Fishing` |
| `2` | Forest | `Farm_Foraging` |
| `3` | Hill-top | `Farm_Mining` |
| `4` | Wilderness | `Farm_Combat` |
| `5` | Four Corners | `Farm_FourCorners` |
| `6` | Beach | `Farm_Island` |
| `MeadowlandsFarm` | Meadowlands | `Farm_Ranching` |

Runtime integer 7 is the data-defined/custom-farm slot. The persisted Meadowlands ID is `MeadowlandsFarm`, not `7`.

Default building locations can come from map properties. Hard-coded fallbacks are farmhouse `(59,12)`, greenhouse `(25,10)`, shipping bin `(71,14)`, and pet bowl `(53,7)`. Four Corners and Beach have special greenhouse fallbacks. This confirms that changing only `<whichFarm>` is unsafe.

Meadowlands also has custom startup logic: fences, a completed coop, two chickens, and animal-house state are created by `Farm.onNewGame`. Hill-top runs repeated mountain-farm updates; Four Corners runs a smaller variant. Templates for those layouts must be generated through the game initialization path, not synthesized by swapping map IDs.

## Serializer behavior

The game serializes the full `SaveGame` first. It then updates `player.saveTime` and separately serializes the player as `SaveGameInfo`. This explains why the samples' player subtree and `SaveGameInfo` differ only at `saveTime`.

Folder/file naming uses only Unicode letters and digits from the farm save name, followed by `_` and `uniqueIDForThisGame`.

## Product decision

The app includes pristine Spring 1 templates for all eight layouts generated by the installed Stardew Valley 1.6.15 executable. Each fixture went through the normal character-creation/new-game path with the intro skipped, so it includes randomized terrain, map-aware default buildings, generated world state, and layout-specific initialization such as Meadowlands' starter coop and chickens. The layout selector loads the corresponding complete fixture instead of rewriting `whichFarm`.

The exact initial-generation path is now confirmed: `Game1.loadForNewGame` resets calendar/world state, instantiates the selected `Farm` map, calls `AddLocations`, adds map-aware default buildings, runs layout-specific `Farm.onNewGame`, adds NPCs, and generates the selected bundle set. The first-day transition then performs the normal location/day updates. This is why an XNB map alone is insufficient as a complete save template.

A later developer tool should invoke that real path to produce a fixture matrix for every layout and option set. The current decompiled branch's desktop target has unresolved browser-port fields, so the checked-in known-good game save is used instead of claiming synthetic templates are canonical.

## Map metadata extraction

`tools/map-extractor` now loads the eight real farm XNB maps through the source tree's FNA `ContentManager` and xTile reader. It emits only coordinate classifications into `src/maps`; it does not copy map artwork or tilesheets.

The static buildability classification mirrors the relevant source checks:

- a `Back` tile must exist;
- `Water`, blocking `Passable`, and `NoFurniture` tiles are rejected;
- blocking `Buildings` layer tiles are rejected unless marked `Shadow` or `Passable`;
- `Buildable=F` is rejected;
- `Buildable=T/true` or `Diggable` is required.

The app separately validates map bounds, full building footprints, current entities, and building overlap. The extractor also reads `Data/Buildings`; generic exterior buildings are initialized from those dimensions/doors. Stable, Fish Pond, and Junimo Hut are emitted with their source-defined `xsi:type`; their IDs use browser-generated RFC 4122 UUIDs, matching the game's `GuidHelper.NewGuid()` → `Guid.NewGuid()` path. Buildings with instanced interiors require complete serialized interior fixtures, unique indoor names, and type-specific initialization. The first implementation is an empty base Coop backed by a sanitized `AnimalHouse` fixture; barns, sheds, and slime hutches still need their matching fixture data. Dynamic game conditions and modded map overrides require a matching imported template and in-game verification.

## Progression controls

The Community Center completion option follows the game's own `DebugCommands.CompleteCc` behavior: it adds the six `cc*` room-completion mail flags and marks all six `CommunityCenter.areasComplete` entries. Greenhouse repair sets `Farm.greenhouseUnlocked` and adds `ccPantry`, matching the normal unlock check in `Farm.DayUpdate`.

Friendship controls patch `Farmer.friendshipData`; source constants confirm one heart is 250 points. Missing residents are added using the current serialized `Friendship` shape.

Bundle remix mode is intentionally not rewritten yet. `Game1.GenerateBundles` chooses and generates bundle definitions during new-game initialization using the seed; the resulting `bundleData`, bundle progress, and reward dictionaries form one generated set. The eventual option needs game-generated template variants rather than a cosmetic flag.
